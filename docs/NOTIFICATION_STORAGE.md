# 通知去重與 schema 10

付款 runtime 現在要求 schema 10；啟動先以唯讀方式確認通知資料表，再建立付款 Store，避免失敗啟動先改動付款標記。一般試用仍建立 schema 4，既有 schema 9 可供資料維護，但不能啟動包含通知的付款 runtime。

## 明確離線升級

先以 billing_migration.prepare_storage 完成 4 → 9，再以 notification_migration.prepare_notifications 完成 9 → 10。兩步都不在啟動時自動執行。後者要求服務離線、無未完成錄音／收件、資料庫完整，持有維護鎖與 SQLite 寫入保留鎖，先建立可還原的加密備份，再在同一交易建立通知表與更新版本；錯誤會回滾。維持原付款政策標記，不開啟或關閉付款。

此次未在正式主機執行升級。舊服務不可開啟新版本；回復須把升級前備份還原到新目錄，不原地降版。

## 去重行為

驗證身分與通知內容後，把訂閱名稱加 messageId 的 SHA-256、正規化通知內容 SHA-256、帳號 ID 與接收時間存入 play_notifications。同一交易更新訂閱 needs_refresh 及版本，所以不會出現只有去重紀錄卻未排查驗的狀態。

同識別碼與相同內容回覆 duplicate，不再次撤銷舊查驗結果；同識別碼不同內容拒絕。主機重開仍有效。紀錄保留 90 天，在成功處理後續通知的交易中清理；超過期限的通知可能重新查驗，但不能直接發放額度。帳號刪除會連動移除紀錄。未知帳號、停用帳號、測試與不支援類型不記入此成功交易去重表。

備份／還原支援 schema 9 和 10，版本 10 要求完整通知表；舊版本出現通知表會被拒絕。還原仍強制所有訂閱重新查驗，因此即使通知已去重，背景工作也不會採信備份中的舊權益。

## 證據

暫存安裝驗證升級前加密備份可恢復 schema 9、schema 10 備份還原保留去重、刪除連動、DDL 失敗回滾、重開後重送、衝突內容拒絕，以及通知表寫入失敗時訂閱狀態一併回滾。這不是正式主機遷移或 Google 真實推送驗收。
