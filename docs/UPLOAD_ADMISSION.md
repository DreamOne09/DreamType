# 上線前接收資源檢查：2026-09-28

## 確認的缺口

原本的 2 MB 檔案限制、120 秒音訊長度和推論 queue 上限，都不能限制「到達 queue 之前」有多少請求同時讀取 body 或解碼。隔離測試中，同一帳號第二個上傳也進入被阻塞的 decoder；第三個慢速 body 也被讀取，沒有在入口拒絕。沒有用真實帳號或對正式服務做大量請求。

## 修正

- `/v2/dictations` 的 POST 在身分驗證後、讀取 body 前取得名額。同帳號最多 1 個，全主機最多 4 個，滿額立即回 429 `upload_busy`。原有檔案與實收 body 大小限制保留。
- 每個 v2 寫入請求讀取 body 的總等待上限為 30 秒，超時 408 `upload_timeout`；失敗、取消、正常完成都釋放接收名額。
- 解碼最多 2 個背景工作，另最多 2 個等待名額，最多等候 2 秒取得解碼名額。三位正常使用者同時提交的測試要求三筆皆接受，解碼同時不超過 2 筆。
- 解碼等待結果最多 15 秒。逾時回 503 `decode_timeout`，尚未加入 queue 或預扣額度。取消／逾時不會終止 Python 執行緒，因此名額只在真正解碼結束時釋放；不會因為斷線又反覆開更多工作。
- 已有 queued/running 工作或剩餘額度為零者，在解碼前拒絕；最終額度仍由 SQLite 原子預留檢查決定。
- 管理 metrics 增加接收／解碼 active、limit，以及解碼 waiting。0.9.14 手機以已知錯誤代碼顯示重試提示，不顯示未信任的任意伺服器文字，不自動重傳錄音。

## 驗證與限制

`test_admission.py` 涵蓋同帳號重入、跨帳號慢速 body 限制、不讀未授權／超大 body、body 逾時後恢復、取消請求仍保留背景工作名額、解碼逾時／錯誤後恢復、已有工作與額度耗盡提前拒絕，以及三人正常提交。帳號、資料庫、錄音及 decoder 均為隔離合成資料。

這是有範圍的原始碼與行為審查，不是第三方安全認證或全站滲透測試；沒有完成依賴 CVE 掃描。本次沒有發現測試涵蓋的跨帳號讀取／用量回執檢查被繞過，不能推論所有 API 都不存在問題。

仍需：未登入請求／健康檢查的整體連線限制、登入限流的公平性、持續負載、網路層防濫用，以及對不可中止 native decoder 的隔離。若兩個解碼執行緒永久卡住，本版會維持占用、拒絕新解碼，需管理者重啟；不假裝已能安全終止 Python thread。這些限制也不保證抵擋分散式阻斷服務。私有 `/v1` 仍是主機擁有者金鑰使用，不把其金鑰提供給測試使用者。

Android 本次僅變更錯誤提示，使用 JVM HTTP 合約驗證狀態碼和訊息；最後一次完整原生模擬器仍為 0.9.13。0.9.14 不宣稱已做 Pixel 9／行動網路驗收。
