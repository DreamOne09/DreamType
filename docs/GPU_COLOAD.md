**結論：短測試可運作，但記憶體餘裕不足，不切換正式 ASR。** 下一個門檻是記憶體管理與較長時間的真實流程驗證，而不是再用短句速度宣稱可公開上線。

後續 [Qwen 載入方式調整](MEMORY_TUNING.md) 在相同短測負載中提高可用 RAM，且已套用至正式 Qwen；下面數據保留原始共存輪次，不能當作調整後狀態。Breeze 仍未正式切換。

保留原本 Qwen 與 TranslateGemma 程序，僅卸載 gateway／Turbo，另以 CUDA int8_float16 載入 Breeze。先測凍結的 extended96 公開短句，再保留 Breeze 常駐，對前 6 段辨識結果各呼叫一次中文整理、日文翻譯、英文翻譯。三種處理依序執行，不是同時推論。沒有使用真人或私人錄音。

資源監測從 Breeze 載入前開始，每次查詢後約隔 0.5 秒，涵蓋載入、ASR 與後續文字請求；數值包含桌面及其他程序，不是單一模型配置量，也不能當作精確瞬間峰值。當時的 Windows 與其他應用程式狀態可能影響結果。短測試未出現 OOM，不代表記憶體壓力、換頁或長時間負載已安全。

`pipeline_passed` 只表示這 18 次請求沒有例外且回傳非空文字，**不是翻譯語意正確率**。例如「所以做這項調查」的日文輸出增加了「目的」及省略號；「灌水機器人」可能具有網路語境，模型卻採澆水語境。原 ASR 已辨錯的「取得大功的數據」也只會交給後段處理，不會因此變成正確原文。完整輸入／輸出保留供後續品質檢視。

前一次探測因測試腳本載入 repo 副本而使用錯誤模型授權，18 次文字請求均為 401；不能算成功。修正為明確的執行中安裝目錄，先查核兩個本機模型授權，再重跑。此文件與下方報告只對應修正後一輪。

本輪 Qwen、TranslateGemma 與 Tunnel 的程序在測試期間保持相同，完成後恢復原 Turbo 服務及維護排程，健康與下載入口驗證通過。準備至恢復約 67 秒。手機仍使用原正式模型，沒有趁測試永久切換。

## 重跑工具與限制

`scripts/check_gpu_coload.py --runtime-root <實際執行中安裝目錄> --model breeze --output <報告>` 使用安裝目錄下的本機模型設定，沒有上傳雲端；先加 `--verify-only` 可以只驗證權重及 96 段音檔。音檔位置仍為 repo 的 work/asr-comparison/audio。

呼叫者需先安排維護排程與 gateway 的停止／恢復，保留 Qwen 19871 及 TranslateGemma 19873；腳本本身不操作服務。不要在 Turbo 仍佔用 GPU 時直接跑。報告有失敗請求時腳本回傳非零狀態，不能只看 ASR 的 `complete`。本輪尚未覆蓋手機網路、完整 API 佇列、自然長口述或其他翻譯目標。
