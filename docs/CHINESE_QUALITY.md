# 台灣中文品質驗收

目標是讓台灣使用者放心口述，不能以「有回傳文字」等同正確，也尚不能宣稱品質超越 Typeless。

## 2026-09-22：避免截斷中文整理

原本整理服務只檢查回傳文字是否非空。模型即使因輸出上限而中途停止，也可能把半段文字當成成功結果。

現在只接受模型明確正常完成（`finish_reason: stop`）的整理結果：

- 語音路徑保留完整辨識原文，回傳 warning；現有 Android 鍵盤顯示「排版暫時失敗，已保留辨識原文」。
- 純文字整理端點回傳 503，不交付半段文字。
- 這保護的是「模型有回報截斷」；不能偵測模型正常結束但自行漏掉內容，也不保證語音辨識本身沒有漏字。

驗證：36 項 Python 測試通過，包含 length、content_filter、缺少結束原因三種不完整結果，以及正常完成結果。更新家中服務後，實際 HTTPS Android Java 測試通過登入、偏好、排隊辨識與用量流程（短測試 3.77 秒）。並非 Pixel 9 實機驗收。

## 下一階段仍須驗證

新增可重跑的 12 個合成文字案例：`tests/quality/taiwan-chinese.json`，涵蓋日期修正、金額、條件、地名、人名、中英夾雜、列舉與識別資料。用 `scripts/check_chinese_quality.py --output work/chinese-report.json` 在已啟動的本機服務執行。文字及結果皆為人工編寫的合成資料，非使用者錄音。HTTP 200 不等於語意正確，需閱讀輸入與輸出。

本輪發現模型會把電話 `0912-003-456` 寫成少一碼。現已比較整理前後的結構化識別資料（電話、網址、信箱、部分英數訂單格式）及出現次數；不一致時拒絕整理結果，語音路徑保留原文。這不涵蓋所有識別碼格式、口述數字或辨識階段的錯字。含明確修正的識別碼也可能退回原文，寧可請使用者確認，不推測其意圖。

第一輪文字報告有 11 件回傳文字，1 件因識別資料變動被拒絕。後續加入逐次請求的識別資料替換：模型只整理含暫存標記的文字，標記需各出現一次且保持順序，才放回電話等原值，再次驗證識別資料一致。映射不跨帳號或請求共用，也不持久保存。

40 項 Python 測試通過，包括標記遺失、重複、順序改變、未知標記、原文含相似標記的碰撞，以及真實格式化函式的回填／失敗保留路徑。實際模型的原電話案例與雙信箱、雙電話、帶編號清單均能整理並保留原值；明確改口更換編號的案例仍會被拒絕整理，供使用者確認原文。

最新文字報告為 `tests/quality/taiwan-chinese-report.json`。HTTP 成功只證明有結果，贅詞案例改善，但列表仍有輸出不一致，**不是所有語意與排版品質全部通過**，也不是與 Typeless 的比較結果。

- 台灣地名、人名、公司名與中英夾雜，不能只靠文字提示詞測試替代真實口音錄音。
- 自我修正、否定、日期、金額與共用條件，在長篇整理後仍完整。
- 個人提示詞只調整文風，不能擅自替使用者回答問題或新增需求。
- 同一批取得同意的錄音與 Typeless 做盲測，比較錯字、漏意、修正時間及延遲，才有「更好用」的證據。
- Pixel 9 的鍵盤高度、單手操作、App 切換、Surfshark 行動網路與加密重試仍待實機驗收。

目前仍是封閉試用；商店、付款、固定入口與備援等差距另見 [正式使用差距](PRODUCTION_STATUS.md)。
