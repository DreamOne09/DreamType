# 真實推論階段耗時（2026-09-28）

為找出多人長翻譯排隊的瓶頸，透過運作中主機的私有 HTTP gateway 依序送入公開音檔串接／截斷片段。使用正式 Turbo、Qwen 與 TranslateGemma 設定，沒有帳號佇列等待，也不含手機網路。這是效能探測，不是自然長口述或翻譯品質驗收。

| 錄音／功能 | 辨識秒數 | 文字處理秒數 | 主機總秒數 |
|---|---:|---:|---:|
| 5 秒繁中整理 | 0.538 | 0.133 | 0.857 |
| 60 秒繁中整理 | 0.810 | 1.191 | 2.222 |
| 60 秒翻英文 | 0.804 | 5.485 | 6.509 |
| 60 秒翻日文 | 1.088 | 6.330 | 7.634 |
| 60 秒翻泰文 | 1.080 | 14.206 | 15.518 |
| 60 秒翻馬來文 | 1.140 | 13.350 | 14.733 |

[原始結果](evidence/inference-stages/profile.json)只保留時間與字數，沒有原文或翻譯內容。每個情境只有一次完整量測，包含先後執行順序的快取／暖機差異，不代表平均值、百分位或服務保證。

首次探測在 60 秒整理時收到 fallback 警告，舊版探測器因此停止，沒有保存該次完整時間與內容；後續改為明確記錄 `formatting_fallback`，不能把退回辨識原文當作整理成功。上表完整輪次没有回退，但先前觀察到的不穩定仍存在；沒有據此修改或放寬原意保護。素材是互不相關短句串接，不能据此判定自然長口述的失敗率。

## 下一個優化方向

這組長翻譯主要時間花在文字模型；只更換 ASR 或增加排隊長度不會解決它。正式 TranslateGemma 使用 10 層 GPU offload、4 個 CPU threads；泰／馬來文目前經英文橋接，為兩次翻譯，日文則有已測試的直接路線。後續應先在保留同一模型、相同內容及品質檢查的情況下比較 CPU threads／運算配置，再評估分階段排程。不能僅因直接翻譯更快，就省略翻譯品質與否定／條件保留檢查。

目前沒有因此變更模型、GPU 記憶體配置、worker 數或翻譯路線，也沒有購買外部服務。更多推論 worker 會撞到既有單一 GPU 鎖，並不自動提高容量。

重跑：`python scripts/profile_inference_stages.py --runtime-root <安裝根目錄> --manifest <公開音檔manifest> --output <報告.json>`。開頭要求正式佇列空閒，但不鎖住稍後到達的正式請求，僅在低使用量時執行。
