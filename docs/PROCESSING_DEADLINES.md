# 整段處理時限

2026-10-18。修正帳號服務先逾時、內層推論仍未結束的時限不一致。

原本 `LocalProvider` 只等待 100 秒；ASR 冷啟動與辨識各有 60 秒，翻譯的每一段 HTTP 又各等 90 秒。中文翻泰文／馬來文等經英文中轉時，整體可能超過呼叫端的等待時間。HTTP 的讀取閒置時限也不限制持續慢慢回傳資料的總時間。

## 新的層次

| 範圍 | 時限與行為 |
|---|---|
| 音訊解碼 | 保留既有最多 2 秒等待、15 秒解碼預算；原生解碼子程序本身 12 秒期限 |
| GPU 等待 | 保留 5 秒；忙碌明確回覆，沒有無限新增推論 |
| ASR 一次操作 | 冷啟動與辨識共用 60 秒，超時終止並回收子程序；回收另有最多 10 秒等待 |
| 整理或翻譯 | 全部模型呼叫合計 90 秒，包括翻譯中轉與英文分段，不是每段重新計時 |
| 帳號到本機推論 API | 整次 190 秒，包括持續緩慢回應；大於內層正常上界，避免先丟棄結果 |
| 帳號佇列單筆工作 | 保留 240 秒外層限制及原有失敗退還額度行為 |

常數在 `processing_budget.py`。這些是最長等待／失敗保護，並非速度承諾；作業系統程序建立、排程或驅動卡住不具硬即時保證。

整理時限到達：回傳完整辨識原文與 warning，不把它算成成功整理。翻譯時限到達：回覆 503，不把原文冒充翻譯。文字整理 API 回覆失敗，原文字串未改。取消仍以取消傳播，不偽裝成成功或逾時；ASR thread 必須真的結束才能釋放其 GPU 鎖。

## 驗證與範圍

- 真實測試子程序的冷啟動與處理各自可在單段預算內完成，但合計超標時必須終止，下一筆可恢復。
- 兩段合成翻譯共用同一時限；取消會關閉第二段。
- 持續送出小量位元組的 HTTP body 仍被整段時限中止且關閉。
- 真實閘道路由的整理保留原文、翻譯拒絕假結果、文字整理失敗與 GPU 鎖釋放均驗證。

此修正針對服務內部與帳號工作。Android 的三分鐘輪詢到期仍提示「取回上一筆」，不將它等同伺服器工作失敗。舊私人同步 v1 客戶端與測試網頁另有自身 90／120 秒等待上限，外部代理也可能限制長連線；不宣稱所有舊客戶端可等待完整 190 秒。商用客戶端使用 v2 排隊與結果取回，避免以單一長 HTTP 連線交付錄音結果。

本輪沒有更換 ASR／翻譯模型、增加付款或資料庫版本，也沒有宣稱已驗證 LLM 程序／GPU 驅動故障的強制終止。LLM HTTP 被取消後的 GPU 作業終止仍取決於引擎，與 ASR 可直接終止自有子程序的保證不同。
